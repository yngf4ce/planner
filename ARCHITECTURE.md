# Архитектура LockedLife

## 1. Текущее состояние (v0.1)

### Стек
- **Один файл `index.html`**: разметка, стили (CSS‑переменные, светлая/тёмная тема) и JavaScript (~900 строк, без фреймворков).
- **Telegram WebApp SDK** (`telegram-web-app.js`): тема, вибрация, кнопка «Назад», диалоги подтверждения.
- **Хранилище — IndexedDB** браузера (база `tg-planner`), при недоступности — память (данные теряются при закрытии).
- **Синхронизация — подготовлена, но выключена**: клиент умеет отправлять изменения на `/api/sync` и `/api/photos`
  (очередь `outbox`, last‑write‑wins по `updatedAt`), но **серверной части в репозитории нет**, а в `index.html`
  стоит `<meta name="api-base" content="off">`.

### Хранилища IndexedDB
| Хранилище | Ключ | Содержимое |
|---|---|---|
| `tasks` | `id` | задача: `title, description, photos[], starred, date (YYYY-MM-DD), status (pending/done/postponed), postponedTo/From, createdAt, updatedAt` |
| `diary` | `date` | `text, mood, updatedAt` |
| `photos` | `id` | фото в виде base64 data URL (сжатые до 1280px JPEG) |
| `goals` | `id` | цель месяца: `month (YYYY-MM), title, description, target, progress, done` |
| `rules` | `id` | правило повторения: `title, description, days[] (0 = Пн), start, end, time, paused, done{дата: true}` |
| `accounts` | `id` | баланс: `name, currency (EUR/USD/UAH), initial (центы), color, archived` |
| `categories` | `id` | категория: `name, emoji, color, kind (expense/income), archived` |
| `txns` | `id` | операция: `type (expense/income/transfer), amount (центы), accountId, toAccountId, toAmount, categoryId, date, note, source` |
| `budgets` | `id` (= id категории) | месячный лимит категории в основной валюте: `limit (центы)` |
| `ideas` | `id` | идея: `title, body, tags[], status (new/work/archive), source (app/bot), transcript` |
| `wplans` | `id` | план недели: `week (YYYY-Www, ISO), title, description, done, starred, order, movedFrom` |
| `meta` | `key` | настройки, служебные метки синхронизации |
| `outbox` | `key` | очередь изменений для сервера |

### Основные блоки кода `index.html`
| Блок | Что делает |
|---|---|
| `DB` | обёртка над IndexedDB |
| `S` | состояние приложения (задачи, дневник, текущая вкладка) |
| `render*` | отрисовка вкладок: `renderDay`, `renderCalendar`, `renderMonth`, `renderStats`, `renderDiary`, `renderMore` |
| `allOn(date)` | все задачи дня: обычные + «виртуальные» вхождения повторов (`ruleOcc`) |
| `openMonthForm` | форма «Месяца»: новая цель/задача/повтор, редактирование цели и повтора |
| `openEditor` / `openPostpone` / `openSettings` | нижние «шторки» (sheet) |
| `Sync` | клиент синхронизации (пока не используется) |
| общий обработчик `click` | все кнопки работают через атрибуты `data-act`, `data-task` и т.д. |

### Известные проблемы и риски
1. **Риск потери данных.** Всё хранится только в WebView Telegram на одном устройстве. Telegram/ОС могут очистить
   данные WebView (особенно на iOS). Единственная защита сейчас — ручной экспорт в «Настройках».
2. **Нет сервера**, хотя клиент на него рассчитан (папка `server/` упоминается, но в репозитории её нет).
3. **Монолитный файл.** Добавление финансов, целей, идей и ИИ в один файл сделает его трудным для поддержки.
4. **Дизайн** — светлая бежево‑зелёная палитра, не соответствует целевому стилю Midnight Blue.
5. **Нижняя панель уже занята 5 вкладками** — для «Финансов» и «Идей» нужен пункт «Ещё».
7. **Фото в base64** занимают ~на 33% больше места; при переходе на сервер их лучше хранить файлами в Storage.
8. Дата «сегодня» берётся из часов устройства; часовой пояс пользователя нигде не сохраняется (нужно для бота).

## 2. Целевая архитектура (предложение, бюджет €0)

```
 Telegram ──────────────┐
  │ Mini App (index.html)│ webhook (текст/голос)
  ▼                      ▼
 Хостинг статики     Supabase Edge Function `bot`
 (GitHub/Cloudflare   ├─ проверка secret_token
  Pages)              ├─ дедупликация update_id
  │                   ├─ голос → Groq Whisper → текст
  │ fetch + initData  ├─ текст → LLM → JSON‑команды
  ▼                   ├─ валидация → подтверждение кнопками
 Supabase Edge Function `api`        │
  ├─ проверка подписи initData        │
  ├─ белый список Telegram ID         │
  └─ «серверные действия» ◄───────────┘  (один и тот же набор для приложения и бота)
        │
        ▼
 Supabase PostgreSQL (RLS включён, прямого доступа у клиента нет) + Storage (приватный бакет для фото/голоса)
```

### Ключевые решения
- **Клиент не ходит в базу напрямую.** Все запросы идут через Edge Function `api`, которая проверяет подпись
  Telegram `initData` (HMAC‑SHA256 с токеном бота) и срок её действия. На всех таблицах включён RLS без
  разрешающих политик для `anon` — даже утёкший публичный ключ ничего не даст.
- **Единый слой «действий»** (`create_task`, `add_transaction`, `create_goal`, `get_spending` …) используется
  и приложением, и ботом. ИИ не пишет SQL — он только выбирает действие и параметры, которые потом
  проверяются кодом (схема, существование баланса/категории, права пользователя).
- **Офлайн сохраняется.** IndexedDB остаётся локальным кешем, очередь `outbox` — для отправки изменений.
- **Фронтенд остаётся на чистом JavaScript без сборки** (см. раздел 3), но разбивается на модули.

### Модель данных (черновик)
| Таблица | Назначение |
|---|---|
| `users` | `telegram_id`, имя, `timezone`, `locale`, настройки |
| `tasks` | разовые задачи (как сейчас) |
| `recurring_rules` | правило повторения: `title, days_of_week[], start_date, end_date, paused, time` |
| `recurring_completions` | отметка выполнения правила за конкретную дату (`rule_id + date` — уникальны) |
| `month_goals` | цели месяца: `month (YYYY-MM), title, done, position` |
| `ideas` | идеи: `title, body, category, source (app/text/voice), transcript` |
| `diary_entries` | дневник |
| `accounts` | балансы: `name, currency (EUR/USD/UAH), archived` |
| `categories` | категории: `name, icon, color, kind (expense/income), archived` |
| `transactions` | операции: `type, amount_minor (целое, в центах/копейках), currency, account_id, to_account_id, category_id, date, note, idempotency_key UNIQUE` |
| `budgets` | месячный бюджет по категории |
| `bot_updates` | обработанные `update_id` Telegram (защита от повторной обработки) |
| `pending_actions` | команды бота, ожидающие подтверждения |

Принципы для финансов: суммы — **целые числа в минимальных единицах**; остаток баланса вычисляется из операций
(или пересчитывается в той же транзакции БД); у каждой операции есть `idempotency_key`, поэтому повторная
отправка не создаст второе списание. Переводы между валютами требуют явной суммы зачисления.

Повторяющиеся задачи: хранится **правило**, а не копии. Вкладка «Сегодня» вычисляет, какие правила активны
на дату, и показывает их рядом с обычными задачами; отметка «выполнено» пишется в `recurring_completions`.

## 2.1. Синхронизация (этап 3, реализовано)

- **Таблица `records`** (`supabase/migrations/001_sync.sql`): универсальное хранилище записей планера
  `(user_id = Telegram ID, kind ∈ task/diary/settings/goal/rule, id) → data jsonb, deleted, updated_at, seq`.
  Почему одна таблица: клиент уже умеет синхронизировать «записи» — сервер не требует переписывать приложение.
  Для финансов будут отдельные строгие таблицы (суммы, балансы, ограничения целостности).
- **`sync_push`** — приём пачки изменений; запись обновляется, только если `updatedAt` новее (last‑write‑wins).
- **`seq`** — общий счётчик изменений; клиент хранит последний полученный номер и забирает только новое.
- **Функция `api`** (`supabase/functions/api/index.ts`): проверка подписи `initData` (HMAC‑SHA256 от токена бота,
  срок 3 дня), белый список `ALLOWED_TELEGRAM_IDS`, CORS только для `ALLOWED_ORIGINS`, фильтрация входных данных,
  маршруты `/api/sync`, `/api/photos/:id`, `/api/health`.
- **Фото** — приватный бакет `photos`, путь `{telegram_id}/{photo_id}.jpg`, до 5 МБ.
- **Ограничение:** отметки повторов (`rule.done`) хранятся внутри правила, поэтому если на двух устройствах отметить
  разные дни одного повтора почти одновременно, победит последнее изменение. Для личного использования приемлемо;
  при открытии доступа другим — вынести отметки в отдельные записи.

## 2.2. Финансы (этап 4)

- Хранятся как записи синхронизации (`kind` = `account`, `category`, `txn`, `budget`) — тот же механизм, что у задач.
- **Остаток = initial + Σ доходов − Σ расходов − Σ исходящих переводов + Σ входящих** (функция `balances()`).
  Правка остатка вручную меняет `initial`, история операций не трогается.
- **Защита от двойного списания**: id операции генерируется при открытии формы; повторная отправка = обновление той же записи.
  Бот (этап 6) будет использовать тот же принцип: id операции = производное от `update_id` Telegram.
- **Валюты** не смешиваются: итоги, бюджеты и диаграмма — в основной валюте, остальные показываются отдельно.

## 2.3. Бот Noctis AI (этап 6)

`supabase/functions/bot/index.ts`, таблицы `bot_updates`, `bot_pending` (`003_bot.sql`).

1. Telegram → webhook. Проверяется заголовок `X-Telegram-Bot-Api-Secret-Token`, затем `update_id` записывается
   в `bot_updates` (повтор → игнор), затем Telegram сразу получает ответ 200, обработка идёт в фоне (`EdgeRuntime.waitUntil`).
2. Только личные чаты и только `ALLOWED_TELEGRAM_IDS`.
3. Голос (до 5 мин) → `getFile` → Groq Whisper (`whisper-large-v3-turbo`) → текст показывается пользователю и сохраняется в идее.
4. Текст + контекст (сегодняшняя дата в `BOT_TIMEZONE`, названия балансов и категорий) → Groq `openai/gpt-oss-120b`,
   `response_format: json_schema, strict` → массив действий из фиксированного списка
   (`create_task, create_rule, create_goal, create_idea, add_expense, add_income, transfer, query_spending, query_income, query_tasks, query_balance`).
5. Код проверяет каждое действие: формат дат/времени, сумма → центы, баланс и категория должны существовать
   (не найдено → вопрос пользователю, а не догадка), валюта суммы = валюте баланса, перевод между валютами требует суммы зачисления.
6. Запись — через `sync_push` в `records` (те же записи, что у приложения; id = `b{update_id}x{n}` → идемпотентно).
   Финансы и > 3 действий → `bot_pending` + кнопки «Да, сохранить / Изменить»; остальное — сразу + кнопка «Отменить».
   Смена статуса в `bot_pending` атомарная (`update ... where status = 'pending'`) → двойное нажатие не выполняет дважды.
7. Вопросы («сколько потратил», «что на сегодня», «баланс») считает код по данным, модель только определяет период/фильтры.

## 3. Почему не React (пока)

Текущий код написан без сборки. Переход на React + TypeScript = переписывание всего приложения, установка
Node.js, `npm`, сборка — это много новых понятий сразу. Предлагаемый путь: оставить чистый JavaScript,
разбить `index.html` на несколько файлов (ES‑модули, работают без сборки), подключить Supabase через серверные
функции. Если позже проект вырастет — переход на React можно сделать постепенно.
